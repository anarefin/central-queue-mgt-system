# SRS → Backlog Planner

Turns a large requirements specification into a plan an AI coding agent can build one slice at a time.
Every in-scope requirement ID ends up in exactly one slice, and the dependency order can be checked by a script.

This skill **plans only**. It never writes production code. It ends by asking a human to approve the plan.

## Outputs (all under `plan/`)

| File | Purpose |
| --- | --- |
| `requirements.csv` | Inventory of every requirement ID: area, section, phase, strength, text. Generated by a script. |
| `spec-issues.md` | Contradictions, ambiguities, untestable requirements and open questions, each marked with the slices it blocks. |
| `BACKLOG.md` | Milestones and slices in the fixed format below. The single source of truth for the build order. |
| `traceability.csv` | requirement ID → owning slice → planned test type. It grows into the matrix required by the SRS (for cqms, §27.1). |
| `../PROGRESS.md` | Seeded with slice statuses (`todo`), so implementation sessions can pick up where the last one stopped. |

## Industry practices this skill applies

- **Stable requirement IDs and a requirements traceability matrix (RTM).** Every requirement maps forward to a slice
  and then a test. A requirement with no test counts as not implemented.
- **Vertical slices, not layers.** A slice delivers observable behaviour through every layer it needs (DB → service →
  API → UI or event) and can be demonstrated. Never plan "all entities", then "all controllers".
- **INVEST.** Each slice is Independent (as far as possible), Negotiable, Valuable, Estimable, Small and Testable.
  Aim for one agent session, or 1–3 developer-days, and at most about 10 owned IDs.
- **Walking skeleton first (M0).** The thinnest end-to-end path runs in CI and the installer before any breadth is
  built: auth, one endpoint, one screen, one migration and one deployment.
- **Risk-first ordering.** The hardest and least certain parts come as early as their dependencies allow. Examples:
  concurrency, ordering algorithms, realtime delivery with replay, multi-node behaviour. Unknowns get a timeboxed
  **spike** slice whose output is an ADR, not a feature.
- **Contract-first.** API and event contracts (OpenAPI and event schemas) are fixed in the slice that introduces them,
  before any consumer slice starts. This lets backend and frontend slices run in parallel.
- **NFRs are not a phase at the end.** Each NFR is handled in one of three ways:
  - **Constraint:** part of the Definition of Done for the slices it touches, e.g. security or i18n.
  - **Gate:** enforced automatically in CI, e.g. ArchUnit boundaries, a secured-endpoint test, a lint rule.
  - **Owned slice:** needs its own work, e.g. a load-test harness or a backup/restore drill.
- **Definition of Ready (DoR) and Definition of Done (DoD).** A slice cannot start while it has an unresolved
  blocker in `spec-issues.md`. DoD comes from the SRS (for cqms, §27.5), plus "all tests green and traceability updated".
- **Rolling-wave planning.** Milestones M0–M2 are planned in full detail. Later milestones are sketched and refined
  when the preceding milestone finishes.
- **Every milestone ends in a demonstrable, releasable increment** tied to named UAT scenarios.
- **Phase-2 seams.** Deferred requirements are not built. The interface or extension point they need is listed
  under `Seams:` in the slice that owns that area, so later work adds an implementation instead of rewriting.

## Procedure

### Step 0: Locate inputs and protect the context window
Find the SRS, the glossary (e.g. `CONTEXT.md`) and the ADRs (e.g. `docs/adr/`). Read the SRS **table of contents**
(`grep -n '^#' <srs>`) before anything else. Never load a long SRS whole into context. Read it section by section,
or split the work across subagents by functional area. Read the glossary and ADR titles in full, since they are short.

### Step 1: Build the inventory
```bash
python3 .claude/skills/srs-backlog-planner/scripts/extract_requirements.py "<srs.md>" -o plan/requirements.csv
```
It prints totals by area, phase and strength. It also reports duplicate definitions, IDs that are referenced but
never defined (often example IDs in a conventions table, which a human should confirm), and requirements with no
MUST/SHOULD/MAY.

If the SRS uses a different ID scheme, pass `--id-regex`. If the script finds no IDs, stop and tell the user.
An SRS without stable IDs has to get them first.

### Step 2: Spec health check → `plan/spec-issues.md`
Go through the spec **one functional area at a time**. Run subagents in parallel when there are more than about
5 areas, and give each one its sections, the glossary and the ADR list. Record each finding as:

```
### ISSUE-<n> · <short title>          [blocker | needs-decision | cosmetic]
- Where: §x.y, FR-XXX-nnn (line N)
- Problem: <contradiction / ambiguity / untestable wording / missing acceptance criterion>
- Proposed resolution: <option(s)>; if a design decision → "ADR needed"
- Blocks: S-... (fill after Step 4)
```

Look for:
- **ADR vs SRS drift.** Diagrams and prose that contradict an accepted ADR.
- **Glossary violations.** Terms the glossary says to avoid, or synonyms for the same concept.
- **Untestable wording.** "fast", "user-friendly" or "appropriate" with no measurable target.
- **State or data mismatches.** A requirement that relies on a state, field or event the state machines and data
  model do not define.
- **Unticked open questions**, and which requirements they affect.
- Duplicate IDs and dangling references from Step 1.

**Report issues. Never fix the SRS silently.** Fixes belong to the user, or to a spec/ADR update they approve.

### Step 3: Dependency layers
Before drawing up slices, sort the requirement areas into layers:
1. **Foundation:** skeleton, identity and auth, configuration model, core data model and migrations, state machines,
   API/event conventions, audit, i18n plumbing.
2. **Core domain:** the algorithmic heart (for cqms, the queue engine: ordering, assignment, transfer, miss,
   escalation). Keep it pure and framework-free, and test it hardest.
3. **Channels and user interfaces:** each consumer of the core (for cqms: issuance, agent console, display/audio,
   appointments, visitor PWA, notifications).
4. **Insight:** monitoring, KPIs, reporting read models.
5. **Operations:** installer, upgrade, backup and restore, first-run setup, sizing and load acceptance.

Then pick the riskiest items in each layer and move them as early as their dependencies allow.

### Step 4: Write the slices → `plan/BACKLOG.md`
Use exactly this format. `check_backlog.py` parses it.

```markdown
## M1 · Core queue engine: <demoable outcome in one line>
Exit demo: <what a human sees working>. UAT: U1 (partial), U6.

### S-QUE-01 · Score-ordered waiting list
- Milestone: M1
- Context: queue            <- bounded context / package it primarily touches
- Depends on: S-DAT-01, S-CFG-02
- Requirements: FR-QUE-020, FR-QUE-021, FR-QUE-022      <- owned; each ID owned by exactly one slice
- Constraints: NFR-PERF-003, FR-CFG-103                  <- cross-cutting, satisfied here but owned elsewhere or nowhere
- Gates:                                                 <- IDs proven by a CI gate this slice adds
- Seams: FR-QUE-054                                      <- Phase 2 IDs whose extension point this slice leaves
- Read: §10.2, §10.3, §19.1; ADR-0003, ADR-0004; CONTEXT.md "Score", "Head start"
- Contracts: none | adds GET /queues/{id}/tickets (OpenAPI) | adds event ticket.reordered
- Acceptance: <observable outcomes, in the requirements' own terms>
- Tests: unit (property-based ordering), integration (Testcontainers Postgres)
- Risk: high: anti-starvation edge cases
- Size: M
```

Slicing rules:
- **M0 is the walking skeleton** and holds no business rules beyond auth.
- Contracts come before their consumers. Schema and migration work lives inside the slice that first needs it.
  There is no "create all tables" slice.
- Split a slice that owns more than about 10 IDs, touches more than two bounded contexts, or cannot be demonstrated.
- Group requirements that share state or invariants. For example, everything that can change ticket ownership
  goes together, or into strictly ordered slices.
- Use spike slices (`S-SPK-nn`, output an ADR) for open questions that block design. They carry no owned IDs.
- Every milestone header names its exit demo and the UAT scenarios it advances.
- For concurrency, realtime and time-zone requirements, `Tests:` must name the specific test, such as a race test,
  a replay test or a DST boundary test.

Then write `plan/traceability.csv` with columns
`requirement_id,section,slice,test_type,test_reference,status`, where status starts as `planned`.

### Step 5: Validate
```bash
python3 .claude/skills/srs-backlog-planner/scripts/check_backlog.py plan/BACKLOG.md plan/requirements.csv
```
Fix everything reported as `ERROR`:
- unmapped Phase 1 IDs
- IDs owned twice
- Phase 2 IDs that are built rather than listed as seams
- undefined IDs
- dependency cycles
- dependencies on later milestones
- missing fields

Re-run until the check exits 0. Treat `WARN` (oversized slices) as a strong hint to split. The same script can
run in CI later, so the backlog cannot drift from the spec.

### Step 6: Seed progress and hand off
- Write `PROGRESS.md` with one line per slice: `S-ID | status | notes`.
- Summarise for the user: milestone list with exit demos, counts (IDs, slices, milestones), the top risks, and the
  **blockers from `spec-issues.md` that must be resolved before M1**.
- **Stop and ask for approval.** Do not start implementing.

## Re-planning when the SRS changes
1. Re-run Step 1 to a temporary file and diff it against `plan/requirements.csv` (added, removed or reworded IDs).
2. Map new IDs into existing `todo` slices where they fit. Otherwise create new slices. Never silently change the
   scope of slices marked `done`. Instead, add a follow-up slice and flag it.
3. Re-run Step 5 and summarise the delta for the user.

## Project defaults for cqms
- **Backend:** one Spring Boot app, one package per bounded context: configuration, issuance, queue, appointment,
  session, notification, reporting, identity, audit (ADR-0010). Use those names in `Context:`.
- **Data:** PostgreSQL 14+ with Flyway. Realtime fan-out uses `LISTEN/NOTIFY`, and scheduled jobs use ShedLock.
- **Frontend:** Next.js apps for kiosk, console, display, admin and the visitor PWA. API types are generated from the
  OpenAPI contract, and realtime payloads are typed from the event schemas (§21).
- **Candidate CI gates:** ArchUnit package boundaries, the "every controller method secured or listed public" test
  (FR-CFG-108), both language packs complete (DoD §27.5-3), and `check_backlog.py`.
- **Suggested M0 walking skeleton:** Spring Boot + Flyway + JWT auth (§20.2) + one secured endpoint + one Next.js
  page consuming the generated client + an offline installer bundle skeleton (NFR-POR-004).
