Setup wizard, go-live, config bundle and versioning

The first-run wizard with its real test token, the go-live gate and its ten-item missing list, the signed configuration bundle, and per-area version history and revert.

Setup wizard (/admin/setup/)

Role: system_admin or org_admin. Eight steps, each a status of Done or Not done yet, read live off the real Site, Zone, Counter, Service, user and device tables so it can never drift from what exists.

StepDone when
Vertical profilea profile is active (profile_applied)
Organisation and sitesat least one active Site (org_and_sites)
Zones and Countersa Zone and a Counter exist (zones_and_counters)
Services and numberinga Service exists and numbering is in place (services_and_numbering)
Users and rolesmore than the bootstrap admin exists (users_and_roles)
Register devicesat least one device is paired (devices_registered)
Test print and announcetest token issued, printed, called and announced
Go liveall of the above; records a go-live timestamp

The test token is a real Ticket through the normal pipeline: issue it, confirm it printed, have an Agent call it from an open session in the Console, then confirm the Zone announced it. Printing and announcing are explicit human confirmations; a chime having played is never inferred from the ticket reaching called.

Config bundle (API only)

A signed JSON bundle clones priority classes and channel/Service defaults, routing strategies, numbering rules and business-hours weeks between environments of the same version (production to staging or training). The Site, Service group and Service ids it keys by must already exist on the target. It needs an organisation-wide caller (no site_ids claim), and both installations must carry the same secret:

QMS_CONFIG_BUNDLE_SECRET=<shared secret>     # qms.config.bundle.secret; blank = export and import both refused

Import applies all or nothing in one transaction, and answers applied_counts per kind of row.

Version history and revert

Four areas keep an append-only history, one row per change with author and time: priority classes, routing strategy (per Service group), numbering rules (per Service or group) and business-hours weeks (per Site or Service). A revert re-applies the earlier state through the same validation and audit path as a normal edit, so a revert is itself one more version. GET .../impact previews what a change would affect.

The Admin screens for priority classes, routing strategy and numbering show a Version history panel with a revert action. Business hours has no admin page yet, so its history and revert are API only (see Appendix E).
