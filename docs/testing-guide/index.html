cqms testing guide

How to use and test every feature of the Queue Management System, for business users and for developers.

What this is

A single guide to using and testing every feature of the cqms Queue Management System, written for two readers:

  • Business users doing UAT. Every test case has numbered UI steps in plain words, the result to expect, and a Pass / Fail / Notes box. Print the sign-off sheet at the foot of each page and tick down it.
  • Developers and automation engineers. Open the *Dev / API* block on a case for the curl request, the HTTP status, the details.reason, the audit event and the automated test that already covers it.

Everything is static HTML: no build, no network, light and dark mode, and it prints. Open this file straight from disk.

How to run a case

  1. Bring up a stack and create the test users (Getting started).
  2. Pick the page for the feature. Read its short introduction: it states the rules, the bounds and the settings you may need to change.
  3. Do the Steps in order, as the role named on the card, in a private browser window per role.
  4. Compare with Expected. Tick Pass or Fail; write anything odd in Notes with the build, date and your name.
  5. To see *why* something is refused, open Dev / API; the same reason is listed in Appendix A with the exact message a user sees.

Case types: <span class="badge happy">happy</span> the normal path; <span class="badge unhappy">unhappy</span> a validation error, refusal, permission denial, conflict, limit or failure; <span class="badge edge">edge</span> a boundary, race or unusual state.

Case ids look like TC-SES-014: three-letter area, three digits, never renumbered. The area codes are in the table below.

Read this before you start: honest limits

This guide describes the product as built. Where the code and the older documents disagreed, the code was believed. Three things you will meet:

  • Some features have an API but no screen (appointment check-in, issuance rules such as hours and caps, zone voice settings, remote-join rules, users and approvals, and more). Their cases give curl steps. The complete list is in Appendix E.
  • Five of the twelve SRS UAT scenarios (U2, U3, U4, U7, U10) need a server clock and cannot be run from a browser. Each is covered by a named integration test; see Automated suites.
  • Only three of the five profiles (banking, healthcare, producer services) have an automated Playwright scenario. Government and Generic are covered by hand here.

Start here

  • Demonstrating the Aarong Central Queue Management pitch deck? Load the demo data and follow the Aarong walkthrough (deploy/demo/aarong/).
  • New to the system? Follow the industry walkthroughs: one day in the life per profile, with checkpoints.
  • Setting the system up for a client? Industry configuration for all five profiles, ending with adapting *generic* into a telecom service centre using configuration only.
  • Checking who may do what? Roles and permissions has an allow and a deny case for every permission.
  • Running the automated suites? Automated suites.

Printing

Use the browser's Print. The navigation is hidden, cases do not split across pages, and the sign-off sheet at the foot of each feature page starts on a new sheet. Choose Background graphics if you want the coloured case type edge.
