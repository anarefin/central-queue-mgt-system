Webhooks, service accounts and the host API

Registering an outbound webhook and proving its signature, retries, replay and SSRF refusals; creating a service account and using its token.

Outbound webhooks (/admin/webhooks/, config:org_sites_zones)

An external system registers an endpoint to receive a subset of the realtime hub's events.

  • Endpoint fields: description (at most 200), url (HTTPS only, at most 2000), event_types (at least one from the closed set below), optional secret (generated server-side when blank).
  • Closed event set (20): ticket.issued, ticket.called, ticket.reannounced, ticket.missed, ticket.serving, ticket.held, ticket.completed, ticket.no_show, ticket.cancelled, ticket.transferred, ticket.position_changed, queue.estimate_changed, session.opened, session.break_started, session.break_ended, session.closed, alert.raised, alert.acknowledged, device.command, config.changed. An internal-only event such as ticket.forfeited is never delivered, even if named.
  • SSRF defence: a URL that resolves to a private, loopback or link-local address is refused at save with validation_failed and a reason beginning unsafe_endpoint:. Delivery re-applies the same check.
  • Signing: each delivery carries X-QMS-Webhook-Signature (lowercase hex HMAC-SHA256 over "<timestamp>.<body>"), X-QMS-Webhook-Timestamp, X-QMS-Webhook-Id and X-QMS-Webhook-Event. The secret is shown only on create or rotate and is never readable back.
  • Retries: exponential backoff 30 s x 2^(attempt-1), up to 6 attempts, then terminally failed. One attempt longer than 5 s counts as failed.
  • Deactivation is soft. Rotate invalidates the old secret at once. Replay re-queues a delivery (needs config:org_sites_zones, since it is a real POST to an external system; the log itself needs audit:read).

A quick local receiver for the cases: python3 -m http.server will not verify signatures. Use any HTTPS request bin you control; because private addresses are refused, a receiver on localhost cannot be used except by setting qms.webhook.allow-insecure-endpoints-for-tests=true on a throwaway test stack only.

Service accounts and the host API

A service account is a non-human principal (host_system) created by an administrator with user:manage (POST /service-accounts {label, site_ids}). The client id and secret are shown once. It exchanges them for a short-lived token at POST /auth/service-accounts/token and then calls POST /host/tickets (see Issuance). Deactivating an account stops it at once. Failures audit service_account.auth_failed with a reason unknown_client_id, inactive or bad_secret, but the response is identical in each case.
