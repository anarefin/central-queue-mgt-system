Journeys and multi-stop visits

One visitor, several Services: ordered and unordered journeys, templates, the paused state, and the four journey refusals.

Model (ADR-0007)

Every Ticket belongs to a Visit. A Journey is an optional plan of stops on a Visit, an ordered or unordered list of Services from a template or ad hoc. A Journey holds Services, and a Ticket realises a stop.

  • Ordered: only stop 1 issues a Ticket. When it is completed, the next stop's Ticket is created automatically, inheriting the visitor's Priority class. Stop 2 stays planned until then (FR-QUE-061).
  • Unordered: every stop's Ticket is created up front and all share one visit_id (FR-QUE-062).
  • One place at a time (FR-QUE-063): when one Ticket of a Visit is called, the visitor's other waiting Tickets become paused (no wait accrues) and return to waiting when the visitor is free.
  • A Journey never crosses Sites.

Two switches must both be on: the org-wide journey feature flag (Healthcare and Producer services profiles ship it on) and the journey setting enabled (Admin API PUT /journey-settings {"enabled":true}, default off). The flag is checked first: feature_disabled beats journeys_disabled.

Templates belong to a Service group (POST /service-groups/{id}/journey-templates {name_i18n, ordered, display_order, service_ids}), can be deactivated, and are offered at Reception's *Journey* picker. Template creation and the journey-settings switch are API only: there is no Admin screen for them.
