Queue engine: score, head start, escalation, strategies, dry run and wait estimates

How the next Ticket is chosen, how to prove it with numbers a tester can check by hand, and what each strategy does differently.

The ordering rule (FR-QUE-020, ADR-0003)

For a waiting Ticket:

score = effective_wait_minutes + headstart_minutes + appointment_bonus
        + escalation_bonus + score_adjustment_minutes

The highest score is served first. Ties break by earliest creation time, then lowest ticket id. All terms are minutes, so every waiting Ticket's score grows at the same rate: a class's head start takes effect on arrival and never has to be "caught up".

TermMeaning
effective_wait_minutesminutes in waiting (and remote before check-in), excluding time paused
headstart_minutesthe Priority class's head start; Normal = 0
appointment_bonusdefault 15, for a checked-in appointment (qms.queue.appointment-bonus-minutes)
escalation_bonusgrows once real wait passes the class's maximum wait, so the Ticket is served before any lower-priority Ticket
score_adjustment_minutessigned, set once by a positional move (delay, forfeit, Miss re-entry, call timeout); never rewrites the real wait (ADR-0004)

Worked numbers to check by hand

Classes: Normal (head start 0), Senior (10), Priority banking (15, max wait 20).

TicketClassReal waitScore
N1Normal20 min20
P1Priority banking3 min3 + 15 = 18

N1 (20) is called before P1 (18). Change the numbers: if N1 has waited only 10 minutes, N1 scores 10 against P1's 18, so P1 is called first. The rule of thumb: a priority Ticket is served ahead of normal Tickets that arrived less than its head start earlier, and behind any normal Ticket that has waited longer than that (UAT U6).

Strategies (per Service group)

StrategyOrder
weighted_wait (default)by score, highest first; escalation applies
strict_priorityclass first (higher head start first), then creation order; escalation applies
fifocreation order only; class ignored, no escalation

Assignment

  • A Counter draws from all queues it serves, taking the eligible Ticket with the highest score, preferring primary (lower weight) links when scores are within qms.queue.primary-link-tolerance-minutes (default 5).
  • Assignment binds the Ticket to the calling session under optimistic concurrency on ticket.version, so two Counters can never call the same Ticket (ADR-0008).
  • A Ticket targeted at a named agent waits in that agent's personal queue and cannot be drawn by another Counter.

Wait estimate (FR-QUE-040..042)

estimate = (tickets_ahead / max(open_counters, 1)) x rolling_average_handling_time

The rolling average uses the last 20 completed Tickets for that Service at that Site, falling back to the Service's expected_minutes when there are fewer than 5. The estimate is a rounded range in 5-minute steps (for example *about 15-20 minutes*), never stored, and recomputed on every queue change.

Cases

TC-QUE-001

Priority ticket beats a normal ticket that has waited less than its head start

happy
SRS
FR-QUE-020, ADR-0003, UAT U6
Role
reception_operator, agent
Preconditions
A class with head start 15 and a linked Counter.
Steps
  1. Issue Normal ticket N1 for a Service. Wait about 2 minutes.
  2. Issue P1, set its class to a class with head start 15.
  3. Open a session and press F2.
Expected

P1 is called first (score about 15 versus N1's about 2). Repeat with N1 waiting more than 15 minutes longer than P1: N1 is called first.

Dev / API
POST /tickets x2 ; POST /tickets/{id}/priority ; GET /queues/{serviceId} ; POST /sessions/{id}/next

Automated: QueueEngineTest; e2e U6 (u06-priority-headstart.spec.ts)
