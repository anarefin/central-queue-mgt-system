Getting started

Bring the stack up, create one test user per role, pair a kiosk and a display, and reset between runs.

How to use this guide

This guide has two readers and every test case serves both.

  • Business users (UAT). Follow the numbered Steps and compare what you see with Expected. Tick Pass or Fail on the card or on the sign-off sheet at the end of each page. You never need the *Dev / API* block.
  • Developers and automation engineers. Open the *Dev / API* block on a card for the curl request, the HTTP status, the details.reason, the audit event and the automated test that already covers the case.

Words are used exactly as in CONTEXT.md: Site, Zone, Counter, Service group, Ticket, Token number, Re-announce (never "recall"), Miss, Head start (never "weight"), Transfer and Successor ticket. In a profile such as banking the screens may show other words, for example "Customer" for Visitor. That is the terminology feature and is itself tested; see Industry configuration.

The UI is English only in this guide. Bangla packs ship, but no Bangla cases are written here, with one exception that matters everywhere: token numbers are always Western Arabic digits (0-9), even on a Bangla screen (ADR-0011).

1. Prerequisites

  • Docker with Compose v2, and about 4 GB free RAM.
  • A browser. Use a private window per role so sessions do not bleed into each other.
  • curl and jq for the Dev / API blocks.
  • Optional for some mobile cases: a mail catcher such as Mailpit, because the visitor OTP is sent by email (see Mobile visitor).

2. Bring up the stack

export QMS_DB_PASSWORD='choose-one'
export QMS_BOOTSTRAP_ADMIN_USERNAME='admin'
export QMS_BOOTSTRAP_ADMIN_PASSWORD='Admin-Passw0rd-123'
docker compose -f deploy/compose.yaml up -d --build --wait
  • Open http://localhost:8080/admin/. All five apps and the API share one origin: /admin/, /console/, /kiosk/, /display/, /visitor/ and /api/v1. The refresh cookie is SameSite=Strict, so do not put a second proxy on a different host name in front of it.
  • The migrate container runs first and exits; the backend only starts after it succeeds (FR-OPS-020).
  • On plain HTTP to a host other than localhost, set QMS_REFRESH_COOKIE_SECURE=false, otherwise sign-in appears to succeed and then drops you straight back to the login page.
  • The bootstrap variables create the first System Administrator only while there are no users. Once any user exists they are ignored.

Password policy (used by every test user)

RuleDefaultSetting
Minimum length12 charactersqms.security.password.min-length
Character classesat least 3 of lower / upper / digit / otherqms.security.password.min-character-classes
Reuse historylast 5 passwords refusedqms.security.password.history-count
Maximum length72 bytes (bcrypt limit)fixed
Expiryoffqms.security.password.max-age-days

A bad password is refused with 400 validation_failed and details.field (for example new_password when changing a password) and details.rules[] carrying too_short, too_long, too_few_character_classes or reused (reused only triggers on POST /auth/password). If the bootstrap password breaks the policy the backend refuses to start; read docker compose logs backend.

Overriding a setting for a test run

Compose passes only a fixed list of variables to the backend. To change a qms.* setting (for example QMS_QUEUE_HOLD_LIMIT or the SMTP host) create your own override file, keep it out of git, and add it with -f:

# deploy/compose.test.yaml  (yours; not committed)
services:
  backend:
    environment:
      QMS_QUEUE_CALL_TIMEOUT_SECONDS: "20"
      QMS_QUEUE_ANNOUNCE_REPEAT_LIMIT: "2"
      QMS_NOTIFICATION_EMAIL_HOST: mailpit
      QMS_NOTIFICATION_EMAIL_PORT: "1025"
      QMS_NOTIFICATION_EMAIL_STARTTLS: "false"
docker compose -f deploy/compose.yaml -f deploy/compose.test.yaml up -d --wait

Settings that change limits are marked in the cases that need them, and listed with bounds and defaults in Appendix C.

3. Sign in as the bootstrap administrator and set up a session for the API

export BASE=http://localhost:8080/api/v1
export TOKEN=$(curl -s $BASE/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"Admin-Passw0rd-123"}' | jq -r .access_token)

Access tokens live 15 minutes (API-013). Re-run the line when a call answers 401 token_invalid.

Nine roles exist. Five are staff accounts you create; four are not users at all and are covered where they arise.

Use one password shape for every test user: Qms-Test-<Role>-9!. It has 12+ characters and 4 classes.

# a Site first (see Sites, zones and counters), then:
curl -s $BASE/users -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{
  "username":"t-reception","password":"Qms-Test-Reception-9!","display_name":"T Reception",
  "preferred_language":"en",
  "roles":[{"role":"reception_operator","site_ids":["<SITE_ID>"],"group_ids":[]}]}'

site_ids and group_ids scope the role. An empty list means "everything the role may reach". Scope is carried as token claims (FR-CFG-106), and a user cannot grant more than they hold.

An agent must also be a member of the Service group's Team, otherwise they cannot open a session on it: POST /service-groups/{id}/team/members {"user_id":"<id>"}.

5. Pair a kiosk and a display

  1. In Admin open Devices & displays > Device pairing and fleet.
  2. Create a pairing code: kind kiosk (Site) or display (Site and Zone), and a label. The code is 8 characters, valid 10 minutes, single use, shown exactly once.
  3. On the device browser open /kiosk/ or /display/ and type the code.
  4. The device now appears in the fleet list as online and heartbeats every 60 seconds.
curl -s $BASE/devices/pairing-codes -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"kind":"kiosk","site_id":"<SITE_ID>","zone_id":null,"label":"T-Kiosk-1"}'

A fresh browser profile has empty storage, so nothing is paired until you pair it. Pairing survives a reload but not a cleared profile.

Restart without data lossdocker compose -f deploy/compose.yaml restart backendnothing; waiting tickets and open sessions survive (see Operations)

down -v also drops the keys volume, so every access token issued before it is dead. That is expected.

7. Test data conventions

  • One Site per run, named T-<yyyymmdd>-<initials>, code T-<yyyymmdd>-<n>. Site codes are globally unique and match [A-Za-z0-9_-]+. Creating a second Site needs the multi_site flag on, unless it is the very first Site.
  • Prefix every fixture with T-: users, devices, counters, notices, webhooks. Filtering the audit log and fleet by T- then isolates your run.
  • Service prefixes. A token prefix is at most 8 letters or digits. Two active Services at one Site cannot share a prefix.
  • Passwords as above; emails on a domain you own or a mail catcher.
  • Time. Business hours, cut-offs, appointments and reset times are Site-local. Create the Site with a timezone you are physically in (for example Asia/Dhaka) so "now" matches your wall clock.
  • Clock-driven cases (arrival deadline, daily reset, no-show sweep) cannot be forced from a browser. Where a case says *integration only*, run the named test instead; see Automated suites.
  • Do not test on a live deployment. Some cases deliberately lock accounts, revoke devices and fill queues.

TC-SET-005

Plain-HTTP sign-in on a non-localhost host needs the cookie override

edge
SRS
API-017
Role
Operator
Steps
  1. Browse to http://<lan-ip>:8080/admin/ with QMS_REFRESH_COOKIE_SECURE unset.
  2. Sign in and wait for the first silent refresh, or reload.
  3. Restart with QMS_REFRESH_COOKIE_SECURE=false and repeat.
Expected

With the default the cookie is Secure and is not stored over HTTP, so you are returned to the login page after the first refresh. With false the session survives a reload. Use true with TLS in production.

Dev / API
Inspect Set-Cookie on POST $BASE/auth/login: qms_refresh; HttpOnly; SameSite=Strict [; Secure]
