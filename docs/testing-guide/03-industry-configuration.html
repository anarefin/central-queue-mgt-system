Industry configuration guide

How to apply, reset and adapt each of the five shipped vertical profiles using configuration only, ending with a worked example that turns the generic profile into a telecom service centre.

The rule behind this page

There is no if (industry == "bank") anywhere in the product (SRS CFG-001). An industry is configuration: label overrides, feature flags, priority classes, numbering, a starter catalogue and default report/KPI settings. A vertical profile is one JSON file in backend/src/main/resources/profiles/, and a sixth profile is one more file, not one more branch.

Five profiles ship: banking, healthcare, producer_services, government, generic. Only the first three have an automated Playwright fixture. The last two are exercised here by hand.

Common recipe (works for every profile)

  1. Apply. Admin > Setup wizard > *Vertical profile* > Apply profile. Works once, on an installation with no profile active.
  2. Switch or reset. Later, Reset to this profile or Reset to a different profile. Reset re-seeds labels, the six flags and any *missing* priority classes. It overwrites flag and label edits you made but never removes a class that is in use.
  3. Create a Site, Zone, Counter (Admin > *Sites, zones and Counters*).
  4. Seed the starter catalogue. Setup wizard > *Seed starter catalogue* > pick the Site > Seed starter catalogue. It creates the profile's Service group, its starter Services and a group numbering rule. Running it again creates nothing new; it lists each item as *Skipped: already exists* or *prefix already in use*.
  5. Link a Counter to each Service (Admin > *Service catalogue* > Counters) so tickets have somewhere to be called from.
  6. Edit anything the profile set through its ordinary screen: terminology at *Terminology*, flags in the *Feature flags* card, classes in *Priority and queue ordering*, numbering in *Ticket numbering*.

Edits are per language for labels (60 characters maximum), and every edit is audited (label.updated, feature_flag.updated, priority_class.updated).

Configure branding, printed ticket, layouts, languages and templates

These are not part of a profile; every installation sets them. The recipe is the same for all industries.

  • Branding and theme. Admin > *Branding and printed Ticket*: organisation name (max 200), logo URL, primary colour as #rrggbb. One organisation-wide brand themes the kiosk, display, printed token, mobile pages, reports and, from ticket 62, every app.
  • Printed token template. Same screen: tick which fixed fields print (token_number, building, floor, service group, service, visitor code, visitor name, category, counter, issue time, estimated wait, QR code, notice line) and set the notice line (max 500). The preview uses sample data and issues nothing.
  • Display layouts. Admin > *Device pairing and fleet* > a display > layout now_serving_table, split_media, single_counter or summary_board, plus its columns (token and counter are mandatory, service and staff optional), split percent (10-90) and language cycle (0-300 s).
  • Announcement languages, chime and quiet hours. API only, there is no Admin screen for these in this build. PATCH /zones/{id} with announcement_languages (subset of installed languages), chime (chime_standard, chime_soft, chime_alert), chime_volume 0-100, a quiet period quiet_start and quiet_end (both or neither) and max_announce_queue_depth 1-20. The client-side validators exist, but no form uses them yet.
  • Notification templates. Admin > *Notifications*: per trigger, channel and language, with a live preview.

Behaviour of each is tested on its own page: Displays and voice and Notifications. The cases below test the configuration workflow.
