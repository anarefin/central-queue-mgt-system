Roles and permissions

What each of the nine roles can and cannot do, one allow case and one deny case per permission, and direct-URL tests that prove hiding a menu item is not the security boundary.

Roles are fixed in code (FR-CFG-101). Only their display names can be localised. There is no custom-role editor, and there is no case here that creates one.

Things that surprise people, all deliberate:

  • System and Org administrators cannot call, serve or complete Tickets. Only Team Admin and Agent hold ticket:call_serve_complete.
  • Only Reception can issue. ticket:issue is held by no administrator. Agents cannot issue or reprioritise either.
  • Some actions need two permissions. Report export needs reports:run_export and visitor_pii:view. Seeding a starter catalogue needs config:org_sites_zones and config:service_catalogue. A caller with only one is refused 403 forbidden.
  • Two endpoint groups are authorised by role, not by a matrix row: feedback moderation (TEAM_ADMIN) and an Agent's own feedback (AGENT). Neither appears in SRS section 5.2.
  • Some reads are wider than their write. GET /priority-classes is open to ticket:issue (so Reception can pick a class), and GET /setup/feature-flags and GET /labels need only a signed-in user.
  • Sidebar visibility is presentation, not security. The API enforces every rule (FR-CFG-103); the build fails if any controller method has neither @PreAuthorize nor @PublicEndpoint (ControllerSecurityTest, FR-CFG-108).

How to run the allow and deny cases

Each permission below has one allow and one deny case. Sign in as each listed role in its own private window (see Getting started) and attempt the same action.

  • An allow case passes when the action succeeds and the record appears.
  • A deny case passes when the server answers 403 forbidden with the message *You do not have permission to do this.* and nothing is changed. The control may also be hidden; that is convenience, not the test.
  • An S role gets a third case, own-record checks.

Authorisation failures are logged (API-018) and the refusal never reveals whether the target exists beyond what the caller may know.
