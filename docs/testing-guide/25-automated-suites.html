Automated suites and how to run them

Backend unit and integration tests, frontend tests, the Playwright UAT scenarios per profile, the k6 load test with its pass thresholds, and which catalogue cases each UAT scenario covers.

Backend (backend/, Java 25, Spring Boot 4.1, Gradle 9)

CommandWhat runsNeeds Docker
./gradlew testunit and Spring slice tests (*Test); the queue engine suites are pure and DB-freeno
./gradlew integrationTest*IT classes against real PostgreSQL 14 via Testcontainers (no H2, no in-memory substitutes, ADR-0012)yes
./gradlew checkboth (what CI runs)yes
./gradlew test --tests com.qms.queue.QueueEngineTestone classno
./gradlew integrationTest --tests com.qms.session.SessionITone IT (test --tests <IT> fails: ITs are excluded from test)yes
./gradlew integrationTest --tests '*SessionIT.methodName' --rerunone method, forced (Gradle caches passes)yes
./gradlew compileJava compileTestJavacompile and typecheckno
./gradlew dependencyCheckAnalyzeOWASP dependency scan; fails at CVSS 9.0 (needs NVD_API_KEY)no

Reports: backend/build/reports/tests/{test,integrationTest}/index.html, XML under backend/build/test-results/. The forked test JVM runs with a 3 GB heap because the IT suite accumulates about 70 Spring contexts. Tests write signing keys to backend/build/test-keys.

Guard tests worth knowing (they fail the build if you drift):

  • PermissionMatrixTest diffs PermissionMatrix.java and Authorities.java against src/test/resources/permission-matrix.txt, an independent transcription of SRS section 5.2.
  • ControllerSecurityTest requires every controller method to carry @PreAuthorize or @PublicEndpoint (FR-CFG-108).
  • ArchitectureTest (ArchUnit): no package cycles, platform imports no context, the queue package stays free of web and transport types (ADR-0001 seam).
  • ErrorEnvelopeTest / MessagesTest: every emitted code is in the closed set and every error.<code> key exists in every language pack.

Known flakes (recorded in .scratch/qms-phase1/issues/DEPENDENCIES.md): VisitorAppointmentSelfServiceIT and other com.qms.appointment ITs hard-code a Monday date (2026-09-21) that is now in the past, so they can fail on today's date; and an occasional SessionIT / AppointmentCheckInIT failure under resource contention passes on an isolated rerun. Treat a red result as real only after an isolated rerun.

Playwright UAT (frontend/e2e/, per profile)

Standalone project outside the pnpm workspace so pnpm -r test never picks it up. It runs against a real stack; a failure means a product bug, not a stale selector.

# 1. stack up with a bootstrap admin (see Getting started)
# 2. apply ONE profile
TOKEN=$(curl -s $BASE/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"e2e-admin","password":"E2E-Admin-Passw0rd-9"}' | jq -r .access_token)
curl -s $BASE/setup/profile -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"profile_id":"banking"}'
# 3. install once
cd frontend/e2e && npm install && npx playwright install --with-deps chromium
# 4. run, once per profile (config changes between runs, never code)
QMS_PROFILE=banking           QMS_BOOTSTRAP_ADMIN_USERNAME=e2e-admin QMS_BOOTSTRAP_ADMIN_PASSWORD='E2E-Admin-Passw0rd-9' BASE_URL=http://localhost:8080 pnpm e2e
QMS_PROFILE=healthcare        ... pnpm e2e
QMS_PROFILE=producer_services ... pnpm e2e
pnpm e2e:ui        # interactive
VariableDefaultPurpose
QMS_PROFILEbankingselects the fixture; must match the profile already applied
BASE_URLhttp://localhost:8080target origin
QMS_BOOTSTRAP_ADMIN_USERNAME / _PASSWORDnone, requiredthe fixture signs in as this admin

Config: fullyParallel: false (scenarios share seeded state), retries: 0, one chromium project, HTML report in report/, trace and screenshot retained on failure. The fixture turns the multi_site flag on, creates a fresh Site per scenario, seeds the profile's starter catalogue, creates a Reception and an Agent user, and pairs devices through the API. CI job e2e is manual (workflow_dispatch) over the three profiles.

Expected result per profile: 8 passed, 0 failed, 7 skipped (the 5 test.fixme scenarios plus the 2 vertical tests for the other two profiles). Only banking, healthcare and producer_services have a fixture. Government and Generic have no automated scenario.

Things that trip up manual replays of the same flows (the suite already encodes them): wait for the *In service* badge before F5 or F7; an Agent has no ticket:reprioritise (do it as Reception); Pickers load their options on focus (click first); terminology remapping breaks naive text matching (Banking's *Customer* contains *to*).

Load test (deploy/loadtest/token-issuance.js, k6)

SRS 27.4: 3 times expected peak for 30 minutes, section 23.1 targets met throughout, error rate at most 0.1%.

ScenarioRateCalls
issuance_at_three_times_peak3 per second (= 180/min, 3x the 60/min peak)POST /tickets with an Idempotency-Key
console_actions1 per secondPOST /sessions/{id}/next, .../serve, .../complete

Both are open-loop constant-arrival-rate so throughput cannot silently throttle. Pass thresholds:

MetricThresholdSource
qms_issuance_errorsrate < 0.001 (0.1%)SRS 27.4
qms_console_errorsrate < 0.001SRS 27.4
qms_issuance_latency_msp(95) < 2000NFR-PERF-001
qms_console_ack_latency_msp(95) < 500NFR-PERF-003

http_req_failed is deliberately not a threshold: an empty queue (204/404) and the script's own single-shared-session race (409) are expected.

QMS_BOOTSTRAP_ADMIN_USERNAME=admin QMS_BOOTSTRAP_ADMIN_PASSWORD='...' ./deploy/loadtest/seed.sh > deploy/loadtest/.env.loadtest
set -a; source deploy/loadtest/.env.loadtest; set +a
k6 run deploy/loadtest/token-issuance.js                                  # full 30 minute acceptance run
k6 run -e DURATION=2m -e SMOKE=1 deploy/loadtest/token-issuance.js        # quick harness check

Env: BASE_URL, DURATION (30m), SMOKE, ISSUANCE_RATE, CONSOLE_RATE, and required SERVICE_ID, RECEPTION_USERNAME, RECEPTION_PASSWORD (optional COUNTER_ID, AGENT_USERNAME, AGENT_PASSWORD to enable the console scenario). Tokens are refreshed 60 s before their 15-minute expiry so a 30-minute run does not die mid-flight.

Honest status: the tooling is correct and its one real bug (an un-refreshed token expiring 15 minutes in) was fixed, but no run summary survives in the repository, so the section 23.1 targets are not independently evidenced. The matrix marks it partial. Run it and keep the summary. The 99.5% pilot-month availability (NFR-AVL-001) and the 30-minute console training (NFR-USA-005) cannot be produced by an automated run at all.
